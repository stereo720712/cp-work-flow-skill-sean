# CP 合併衝突協助

## 概述

半自動合併流程：Claude 負責分析與建議，使用者負責最終確認，確保金融業務邏輯不因自動合併出錯。

---

## 執行步驟

### Step 1：確認衝突狀態

```bash
cd {repo 路徑}
git status
```

列出所有有衝突的檔案（`both modified`）。

若使用者已指定某個檔案，直接從該檔案開始；否則依序處理所有衝突檔案。

### Step 2：逐檔分析衝突

讀取衝突檔案，找出所有 `<<<<<<<` 區塊。

對每個衝突區塊，分析：

**`<<<<<<< HEAD`（你的改動）：**
- 這段 code 做了什麼
- 為什麼這樣改

**`>>>>>>> {branch}`（對方的改動）：**
- 這段 code 做了什麼
- 為什麼這樣改

**衝突原因：**
- 兩邊是否在改同一個邏輯？
- 是否互斥？還是可以合併？

### Step 3：風險評估

若衝突涉及以下內容，**主動標示高風險**並說明原因：

- 🔴 **金額 / 資產計算**：BigDecimal 運算、手續費、匯率
- 🔴 **訂單狀態流轉**：狀態機轉換邏輯
- 🔴 **分散式事務**：`@GlobalTransactional`、Seata 相關
- 🔴 **資金凍結 / 扣款 / 入帳**：任何涉及帳戶餘額的操作
- 🟡 **Redis 鎖 / 去重邏輯**：可能影響冪等性
- 🟡 **Feign 呼叫 / MQ 發送**：跨服務副作用
- 🟡 **資料庫寫入條件**：WHERE 條件改動可能誤傷資料

### Step 4：給出合併建議

針對每個衝突區塊，給出：

```
📍 衝突位置：{檔案}:{行號}

【你的改動（HEAD）】
{說明}

【對方的改動（branch）】
{說明}

【建議合併方式】
{選擇其中一側 / 兩側都保留 / 手動整合}

【建議的合併結果】
{展示合併後的 code}

【風險等級】🔴 高 / 🟡 中 / 🟢 低
【風險說明】{若有風險，說明原因}
```

若有多個衝突區塊，逐一列出後，最後問使用者：

```
以上是所有衝突分析。請確認每個建議是否採用，或告訴我需要調整的地方，確認後我才會寫入檔案。
```

### Step 5：等待使用者確認

**不要在使用者確認前寫入任何檔案。**

使用者可以：
- 「全部採用」→ 套用所有建議
- 「第 2 個不對，應該要 XXX」→ 調整後再確認
- 「這個我自己來」→ 跳過該衝突

### Step 6：寫入合併結果

使用者確認後，將合併結果寫入檔案，移除所有 conflict marker（`<<<<<<<`、`=======`、`>>>>>>>`）。

```bash
# 確認衝突已解決
git diff {檔案}

# 標記為已解決
git add {檔案}
```

### Step 7：確認所有衝突已解決

```bash
git status
```

若還有其他衝突檔案，繼續處理。全部解完後提示使用者：

```
所有衝突已解決，記得執行測試確認業務邏輯正確後再 commit。
```

---

## 重要原則

- **確認前不寫入**：這是半自動流程的核心，任何檔案修改都需要使用者點頭
- **高風險一定要說清楚**：金額、狀態機、事務相關的衝突，必須明確標示風險並解釋
- **不確定就說不確定**：若無法判斷哪側正確，直接告知使用者需要人工判斷，不要猜
- **一次一個衝突區塊**：若同一檔案有多個衝突，逐一分析，不要一次全丟
